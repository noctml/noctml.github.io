Track 01

공식 튜토리얼

진행 중

Isaac Sim 5.0의 ROS 2 튜토리얼을 따라 camera, robot control, LiDAR, publisher, navigation의 동작과 ROS 2 연동 과정을 확인했다.

001

카메라 모델과 ROS 2 topic

카메라 영상과 ROS 2 message가 연결되는 기본 흐름을 확인했다.

  • Camera Noise 예제의 원본·노이즈 영상 비교
  • Undistorted·Distorted camera와 OpenCV Pinhole·Fisheye 모델 비교
  • camera_info, RGB, depth topic과 camera frame을 RViz2에서 확인
001

원본 영상과 ROS 2 noisy stream

시뮬레이터에서 빙글빙글 도는 camera 원본과 ROS 2로 전달된 noisy stream을 비교해 noise 적용 결과를 확인했다.

002

TurtleBot과 simulation clock

TurtleBot3 Burger를 가져와 controller와 simulation time의 동작을 확인했다.

  • URDF import와 wheel joint drive 설정
  • Differential Controller와 Articulation Controller를 이용한 이동
  • /clock, use_sim_time, publisher·subscriber의 시간 동기화
  • RTF를 이용한 simulation time과 wall-clock time 비교
002

TurtleBot3 URDF와 keyboard 주행

TurtleBot3 URDF를 불러와 Differential Controller를 연결하고 keyboard command로 wheel joint를 제어했다.

003

RTX LiDAR와 TF

LiDAR와 camera sensor를 ROS 2에서 시각화하고 좌표계 관계를 점검했다.

  • 2D·3D RTX LiDAR의 scan과 point cloud 시각화
  • 여러 LiDAR를 사용한 multi-sensor 구성 비교
  • RGB camera pose와 robot TF Tree·TF Viewer 확인
  • Frame 단위 scan과 Publish Full Scan 결과 비교
003-A

RTX LiDAR full scan

2D·3D RTX LiDAR를 함께 구성하고 Publish Full Scan 적용 전후의 point cloud를 비교했다.

003-B

Sensor frame의 TF Tree

TF Tree에서 robot base와 camera·LiDAR frame의 연결 관계를 확인했다.

004

Publisher와 controller 구성

ROS 2 publisher와 외부 controller를 Isaac Sim의 Action Graph에 연결했다.

  • Publish Rate와 QoS profile 설정
  • Generic Publisher와 Static Publisher
  • Joint Control, NameOverride와 외부 message 연결
  • Ackermann Control의 workspace·race track 예제
  • Namespace를 적용한 single·dual robot 구성
004-A

Camera publish 병목

큰 image 해상도로 network 병목이 생기면서 camera topic의 update가 중간중간 끊기는 현상을 확인했다.

004-B

Joint state와 NameOverride

Joint state를 ROS 2 message로 전달하고 NameOverride로 변경한 joint 이름이 반영되는지 확인했다.

005

ROS 2 Navigation

Standalone ROS 2 예제와 Nova Carter navigation의 동작을 확인했다.

  • Periodic·Manual Camera Publishing과 joint state 확인
  • Occupancy Grid와 robot description을 이용한 navigation
  • Waypoint와 다중 waypoint patrolling 비교
  • Hospital scene의 multi-robot navigation과 relocalization
  • MoveIt2와 Action Graph goal 전달, 코드로 goal을 보내는 단계의 실행 실패 확인
005

Multi-robot navigation과 waypoint

Hospital environment에서 여러 robot의 navigation을 실행하고 waypoint 순회와 Occupancy Map Generator로 만든 map을 확인했다.

실행 명령

ros2 run tf2_ros static_transform_publisher \
  0 0 0 0 0 0 base_link base_scan

참고 자료

  • ROS 2 Camera Noise

실행 중 확인한 문제

URDF joint 이름 정리

TurtleBot URDF를 처음 가져왔을 때 joint 이름에 a__name_ namespace가 붙어 controller 설정과 이름을 대응하기 어려웠다. 원본 Xacro를 다시 변환해 namespace가 제거된 URDF를 만들고 wheel joint 이름을 정리했다.

LiDAR frame의 TF 누락

/tf가 발행되지 않아 base_link와 base_scan 사이의 static transform을 직접 발행했다.

RTX LiDAR scan 주기

3D point cloud가 회전 방향마다 끊겨 보이는 원인은 매 frame의 부분 scan을 표시하고 있었기 때문이었다. LiDAR Helper의 Publish Full Scan을 활성화해 한 회전 단위로 바꾸자 더 안정적으로 시각화됐다.

Camera publish 병목

큰 image 해상도로 network 병목이 생기면서 camera topic의 update가 중간중간 끊겼다.

RViz2 depth 표시 문제

서로 다른 publish rate를 적용한 depth 영상이 간헐적으로 검게 보였다. 같은 topic을 rqt_image_view에서 열어 message가 정상적으로 발행되고 있으며 RViz2의 표시 문제임을 확인했다.

Multi-robot localization 이탈

NVIDIA 공식 튜토리얼은 이 예제의 CPU 사용량이 높아 Nav2와 sensor data의 동기화가 어긋날 경우 localization 문제가 생길 수 있다고 설명한다. 실제 실행에서도 일부 robot의 pose가 이탈했고, 우선 RViz2의 2D Pose Estimate로 pose를 다시 맞췄다. 코드로 여러 robot에 goal을 보내는 단계는 정상 동작을 확인하지 못했다.

Python version 충돌

ROS 2 Humble은 Python 3.10, Isaac Sim 5.0 standalone 환경은 Python 3.11을 사용했다. 이 차이로 rclpy를 직접 불러오는 Clock·Carter Stereo·message receiving 예제에서 충돌이 발생했다.

Track 02

가이드 영상 따라하기

완료

Isaac Sim & Isaac Lab 가이드 영상의 흐름을 따라 mesh와 material, rigid body, local asset 예제를 확인한 뒤 Spider Bot과 JetBot으로 범위를 넓혔다.

학습 범위

  • Mesh·material과 rigid body를 이용한 기본 scene 구성
  • Local asset import와 Spot·humanoid·gripper 예제 확인
  • Spider Bot의 URDF·joint 설정과 강화학습
  • JetBot의 differential controller, camera, LiDAR와 collision 구성
G.1

Spot 예제

Isaac Sim의 Robotics Examples에서 Boston Dynamics Spot policy 예제를 불러와 걷는 모습을 확인했다.

G.2

학습 결과와 checkpoint

화면이 많이 버벅여 environment 수를 줄였고, mean reward의 증가와 iteration별 checkpoint 생성을 확인했다.

G.3

Spider Bot asset 구성

Linux에서 강의의 URDF 생성 도구를 사용할 수 없어 공개 URDF를 사용했다. URDF import 후 Physics Inspector로 joint motion을 확인하고 USD로 저장했다.

G.4

Spider Bot 강화학습

강의의 학습 설정에 따라 base link가 바닥에 닿으면 해당 환경의 학습이 종료되도록 Spider Bot을 학습했다.

G.5

Spider Bot 학습 결과 재생

학습 결과를 재생해 Spider Bot들이 균일하게 팔딱팔딱 뛰는 모습을 확인했다. 강의에서 소개한 motion file 기반 수동 제어 예시도 함께 살펴봤다.

G.6

JetBot Differential Controller

Differential Controller를 연결한 뒤 keyboard로 움직여 보니 좌우가 반대로 동작했다. Action Graph에서 좌우 key mapping을 바꿔 방향을 맞췄다.

G.7

JetBot LiDAR와 collision

Action Graph에 LiDAR와 collision 설정을 연결해 장애물 범위 인식과 물리적 접촉을 확인했다.

Spider Bot 환경 오류

Spider Bot 학습 환경을 구성하는 과정에서 file watcher 제한, custom package 탐색, Windows asset path, contact sensor 설정 문제가 차례로 발생했다.

  • max_user_watches와 max_user_instances를 늘려 file watcher 제한 해결.
  • 찾지 못하던 spdrbot3 package를 설치.
  • 환경 파일에 남아 있던 Windows asset path를 Linux 경로로 수정.
  • Contact sensor 오류가 남아 있어 강의에서 제공한 USD로 교체.

Track 03

강화학습 돌려보기

완료

Isaac Lab의 Isaac-Ant-v0 task를 학습하고 TensorBoard에서 학습 로그를 확인했다. 재생 단계에서는 --use_pretrained_checkpoint 옵션으로 제공된 pretrained checkpoint를 불러왔다. 첫 설치에서는 Isaac Sim 5.0과 Isaac Lab 버전이 맞지 않아 재생에 실패했으며, Python·PyTorch·Isaac Sim·Isaac Lab 조합을 맞춘 뒤 정상 실행했다.

학습 범위

  • Isaac Lab 설치와 Isaac Sim·Python·PyTorch 호환성 점검
  • Isaac-Ant-v0 task의 headless training
  • 제공된 pretrained checkpoint로 Ant policy 재생
  • TensorBoard scalar를 이용한 학습 결과 확인
RL.1

Ant task 실행과 학습 흐름 확인

Isaac-Ant-v0 task의 headless training을 실행하고 초기 상태와 학습 완료 결과만 비교했다.

RL.2

Pretrained checkpoint 재생과 TensorBoard 확인

제공된 pretrained checkpoint를 32개 environment에서 재생하고, 학습 과정에서 기록한 TensorBoard 그래프를 확인했다.

./isaaclab.sh -p scripts/reinforcement_learning/skrl/train.py \
  --task Isaac-Ant-v0 --headless

./isaaclab.sh -p scripts/reinforcement_learning/skrl/play.py \
  --task Isaac-Ant-v0 --num_envs 32 --use_pretrained_checkpoint

환경 호환성 문제

Isaac Sim 5.0과 설치한 Isaac Lab 버전이 맞지 않아 학습 결과 재생에 실패했다. 새 conda 환경에 필요한 package를 직접 설치하는 방법도 먼저 시도했지만 해결되지 않았다. 이후 Python·PyTorch·CUDA 조합을 다시 맞추고 Isaac Lab을 v2.2.0으로 고정하자 학습과 재생이 정상 동작했다.

ProblemIsaac Sim 5.0과 Isaac Lab 조합 불일치
Working setupPython 3.11 · PyTorch 2.7.0 · CUDA 12.8 · Isaac Lab v2.2.0
ResultRTX 5070 Ti에서 8,000 epoch 약 1분

Track 04

LIMO SLAM

진행 중

Hospital scene에 AgileX LIMO를 배치하고 camera, LiDAR, IMU와 ROS 2 bridge를 연결했다. 이후 FAST-LIO로 3D map을 만들고 HDL Localization에서 LIMO의 pose를 추정하는 흐름까지 확장했다.

진행 흐름

01Sensor bridge

Camera·LiDAR·IMU topic과 simulation clock 연결.

02LIMO drive

JetBot용 2-wheel 설정과 LIMO의 4-wheel 구조 차이 확인.

03FAST-LIO mapping

LiDAR·IMU를 동기화해 3D global map 생성.

04HDL Localization

Global map에서 LIMO pose 추정과 relocalization 확인.

L.1

Hospital scene과 LIMO asset 준비

Hospital environment를 불러오고 AgileX LIMO asset을 배치해 주행과 sensor 실험을 위한 기본 scene을 구성했다.

L.2

Wheel geometry와 Differential Controller

Wheel joint와 collision mesh에서 wheel base·radius를 확인해 Differential Controller에 입력했다. JetBot의 2-wheel 구성을 그대로 사용했더니 LIMO는 미동도 하지 않았다. 당시에는 JetBot과 LIMO의 wheel 구성 차이를 원인으로 추정했다.

L.3

Camera와 ROS 2 bridge 연결

LIMO 상단의 실제 camera 위치에 맞춰 camera를 배치하고 ROS 2 Action Graph를 구성했다. 공식 camera publish 예제를 참고해 frame ID와 topic을 설정한 뒤 RViz2에서 stream 수신을 확인했다.

L.4

Camera·LiDAR 장착 후 주행

Camera와 LiDAR를 장착한 LIMO를 scene에서 조작하고, 이후 mapping과 localization 실험에 사용할 USD 구성을 저장했다.

KISS-SLAM map에서 localization 실패

처음에는 KISS-SLAM으로 만든 global map을 HDL Localization에 입력했지만 pose가 안정적으로 맞지 않았다. 처음에는 이유를 잘 몰랐지만 KISS-SLAM 실행 과정을 다시 보니 map 자체가 잘못 만들어지고 있었다. Parameter를 조정해도 큰 변화가 없어 FAST-LIO로 map을 다시 만들기로 했다.

Mapping 과정 재확인

KISS-SLAM 실행 화면에서 SLAM 결과가 어긋나는 과정을 확인했다. YAML parameter를 조정해 다시 실행했지만 큰 개선은 없었다.

FAST-LIO로 global map 재구성

FAST_LIO_ROS2를 Docker 환경에서 실행했다. M2DGR dataset으로 먼저 동작을 확인한 뒤 Isaac Sim topic을 연결했지만, 처음에는 mapping이 진행되지 않았다. 혹시 몰라 /clock을 발행하고 LiDAR와 IMU의 publish time을 simulation time으로 맞추자 정상적으로 map이 만들어졌다.

동작을 결정한 조건 이번 환경에서는 LiDAR와 IMU의 publish time을 simulation time으로 통일하고 /clock을 함께 발행한 뒤 mapping이 동작했다.

HDL Localization으로 pose 추정

참고한 hdl-localization-ROS2는 ROS 2 Foxy 기준이어서 Docker image와 package 구성을 Humble 환경에 맞게 수정했다. 먼저 FAST-LIO에서 저장한 PCD와 LiDAR point만으로 localization을 실행했다. 위치 추정은 동작했지만 일부 구간에서는 pose가 벗어나 RViz의 relocalization으로 초기 pose를 다시 지정해야 했다.

ROS 2 Humble 대응 Foxy 기준 실행 구성을 Ubuntu 22.04와 ROS 2 Humble에 맞춘 저장소: noctml/hdl-localization-ROS2-Humble

IMU angular velocity와 회전 안정성

LiDAR-only 결과를 확인한 뒤 Isaac Sim의 IMU topic을 추가했다. IMU publisher에서 angular velocity를 포함했을 때 회전 구간의 localization이 조금 더 안정적이었다. 그러나 회전 속도를 크게 높이면 IMU 사용 여부와 관계없이 pose가 흔들렸고, launch parameter 조정만으로는 충분히 개선되지 않았다.

남은 문제 빠른 회전에서 pose가 흔들리는 원인을 더 확인하고, 수동 relocalization 없이도 안정적으로 동작하도록 보완할 필요가 있다.
